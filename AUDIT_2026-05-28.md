### `src/chess/decision.rs` (173 lignes)

- **Rôle** : Point d'entrée top-level qui résout le `DecisionMode` (env `TCS_AGENT_MODE`) et délègue au search backend via `search_root_via_adapter`.

- **Surface publique** :
  - `DecisionMode` (enum) — sélecteur de mode (Random / Heuristic / Neural / Minimax / Hybrid)
  - `SelectionAuthority` (enum) — qui a sélectionné le coup
  - `DecisionTrace` (struct) — bundle de sortie avec action + metadata
  - `IntoDecisionMode` (trait) — conversion &str → mode
  - `choose_best_action(engine, player)` — entrée simple (lit env)
  - `choose_best_action_for_mode(engine, player, mode)` — avec mode explicite
  - `choose_best_action_with_trace(engine, player, mode)` — avec trace complète
  - `choose_best_action_with_trace_and_context(engine, player, mode, context)` — avec contexte d'analyse

- **Logique clé** : Lit `TCS_AGENT_MODE` pour choisir le mode. Le mode `Random` utilise un `pseudo_random_index` déterministe seeded depuis l'état du moteur (longueur action_log + turn_index + unité count). Tous les autres modes (`Heuristic`, `Neural`, `Minimax`, `Hybrid`) appellent identiquement `search_authority_trace → search_root_via_adapter`. La distinction de mode n'impacte pas le chemin de search — elle est purement étiquetée dans le `DecisionTrace`.

- **Dépendances entrantes** : `chess::root_decision`, `chess::search`, `chess::search_backend_adapter`, `engine::action`, `engine::engine`, `engine::entity::unit`

- **Dépendants** : `ai/decision_controller.rs`, `ai/mod.rs`, `chess/decision_controller_adapter.rs`, `chess/decision_trace.rs`, `chess/decision_trace_bridge.rs`, `chess/search.rs` (re-export), `simulation/selfplay.rs`, `simulation/simulation_runner.rs`, `simulation/teacher_uci_runner.rs`, `tool/conversion_suite.rs`, `tool/puzzle_eval.rs`

- **🚩 Phase 2 flags** :
  - `[ARCHI]` `Heuristic|Neural|Minimax|Hybrid` sont quatre modes sémantiquement vides — tous appellent exactement le même `search_root_via_adapter`. Trompeur vis-à-vis de `neural_agent.rs` qui existe par ailleurs. Candidat à clarification ou fusion.
  - `[DEADCODE]` `SelectionAuthority::{Neural, Heuristic, Unknown}` jamais assignés en pratique (seuls `Search` et `Fallback` sont utilisés). `#[allow(dead_code)]` sur `SelectionAuthority` et `DecisionTrace` le confirme.
  - `[CORRECTNESS]` `pseudo_random_index` est déterministe pour une même position — le mode "Random" produit toujours le même coup à état d'engine identique, ce qui réduit la diversité en self-play.
  - `[ARCHI]` `choose_best_action_with_trace` passe silencieusement `context: None` — les appelants qui veulent la trace d'analyse de partie doivent connaître la variante `_and_context`. Convention implicite non documentée.

### `src/chess/search.rs` (2532 lignes)

- **Rôle** : Moteur alpha-beta negamax central : recherche itérative avec TT, killers, history, null-move, LMR, fenêtres d'aspiration et quiescence.

- **Surface publique** :
  - `RootSearchResult` (struct) — bundle résultat root search (action, score, depth, diagnostics)
  - `search_best_action(engine, player)` — entrée → Action uniquement
  - `search_root(engine, player)` — root search complet
  - `search_root_with_context(engine, player, context)` — avec contexte de partie
  - `order_moves(engine, player, actions, ply)` — ordonnancement de coups (pub(crate))
  - `move_score(engine, player, mv)` — score heuristique d'un coup (pub(crate))
  - `position_key(engine, player)` — hash de position (pub(crate))
  - `root_policy_score(root_key, mv)` — score root policy table (pub(crate))
  - `opponent(player)` — flip joueur (pub(crate))
  - Re-exports : `choose_best_action`, `choose_best_action_for_mode` (depuis decision), `static_evaluate` (depuis eval)
  - Constantes pub(crate) : `PASSED_PAWN_*`, `ROOT_POLICY_*`, `CLEAR_EDGE_MATERIAL`

- **Logique clé** : `search_root_in_place` effectue un approfondissement itératif avec fenêtres d'aspiration (±40 cp, expansion ±80 sur fail). À chaque profondeur, PVS : premier coup en fenêtre pleine, suivants en null-window + re-search si amélioration. Null-move pruning (R=2, désactivé endgame/bas matériel), LMR (réduction d'1 pour coups calmes tardifs à depth≥4 après idx>4), extensions check et coups critiques à shallow depth. Quiescence avec delta pruning SEE. Cinq tables globales `OnceLock<Mutex<HashMap>>` (TT, killers, history, countermoves, root policy) persistent entre les searches. La sélection finale du coup est déléguée à `select_root_move` dans `root_decision.rs`.

- **Dépendances entrantes** : `chess::eval`, `chess::move_features`, `chess::piece_kind`, `chess::practical_policy`, `chess::root_decision`, `chess::search_diagnostics_*`, `chess::search_mirror_ordering`, `chess::search_root_ordering`, `chess::uci`, `engine::*`

- **Dépendants** : `chess/decision.rs`, `chess/mod.rs`, `chess/move_features.rs`, `chess/opponent_response_mask.rs`, `chess/practical_policy.rs`, `chess/root_decision.rs`, `chess/search_backend_adapter.rs`, `chess/search_root_ordering.rs`, `chess/transition_analysis.rs`, `simulation/simulation_runner.rs`, `tool/cli.rs`

- **🚩 Phase 2 flags** :
  - `[PERF]` `eprintln!("DEBUG adaptive_depth: ...")` ligne 892 — print de debug non conditionnel dans le hot path, s'exécute à chaque appel `search_root` en production.
  - `[CORRECTNESS]` `position_key` : hash non-Zobrist (multiply-XOR sur unités triées, encode le type via `piece_value`). Pas de test de collision pour des positions avec des pièces différentes au même carré (ex. cavalier/fou ont `320`/`330` — delta 10, facilement masqué par d'autres termes XOR).
  - `[CORRECTNESS]` Tables `killers`, `history`, `countermoves` jamais réinitialisées entre parties — seul le TT est age-pruné. Des données stale de la partie N peuvent contaminer l'ordonnancement de la partie N+1.
  - `[PERF]` `order_moves` acquiert 3 `Mutex` séquentiellement (TT, killers, countermoves) à chaque appel — appelé O(nodes) fois ; overhead potentiel à haute profondeur ou si parallélisme ajouté.
  - `[CORRECTNESS]` Double extension possible à shallow depth : à depth=1 ou 2, un coup qui est à la fois `critical_move` ET `in_check` peut recevoir `next_depth += 2` (les deux conditions `depth<=2` et `depth<=3` sont vraies simultanément). Comportement non documenté ni testé comme intentionnel.
  - `[TESTS]` Tables globales (TT, killers) non réinitialisées entre tests unitaires — le test-suite est fragile à l'exécution parallèle et peut exhiber des comportements dépendants de l'ordre.

### `src/chess/root_decision.rs` (1406 lignes)

- **Rôle** : Couche de sélection post-search qui affine le résultat alpha-beta via ajustements pratiques : worst-case sampling, filtrage fork, score de transition, diagnostics.

- **Surface publique** :
  - `RootDecisionHooks` (struct) — fn pointers injectés par search.rs (move_score, root_policy_score)
  - `RootDecisionContext` (struct) — contexte de partie pour le tracing (game_id, ply, side, fen)
  - `RootDecisionTrace` / `RootDecisionTraceCandidate` (structs) — trace de sélection complète
  - `RootDecisionBreakdown` (struct) — décomposition des scores par composante
  - `select_root_move(...)` — sélection principale post-search
  - `root_decision_breakdown(...)` — calcul de décomposition de score
  - `root_practical_margin(best_score)` — marge adaptative (22–42 cp selon avantage)
  - `apply_root_practical_adjustments(...)` — ajustements pratiques au score
  - `is_root_fork_move(engine, player, mv)` — détection de fourchette (appelé post-simulation)
  - `should_trace_full_ply(ply)` — prédicat d'échantillonnage

- **Logique clé** : `select_root_move` filtre les candidats dans la marge pratique du meilleur score. Les coups de fork prioritarisés (+500 bonus) ; les coups où l'adversaire peut mater filtres si alternatives sûres existent. Pour les top-N candidats (défaut 8), `opponent_worst_case_value` est échantillonné pour choisir le coup le plus résilient. Classement final : worst_case → search_score → transition_score. Émission de logs diagnostics volumiques via `println!` conditionnel sur env vars (`TCS_ROOT_DECISION_AUDIT`, `TCS_REPLY_SCAN`).

- **Dépendances entrantes** : `chess::eval`, `chess::move_features`, `chess::practical_policy`, `chess::transition_analysis`, `chess::transition_reply`, `chess::uci`, `engine::*`

- **Dépendants** : `chess/decision.rs`, `chess/search.rs`, `chess/search_backend_adapter.rs`, `chess/search_diagnostics_builders.rs`, `simulation/simulation_runner.rs`

- **🚩 Phase 2 flags** :
  - `[DEADCODE]` `root_fork_strength` (ligne 698) et `root_practical_score` (ligne 846) ont tous deux `#[allow(dead_code)]` — jamais appelés en production. `root_fork_strength` semble supersédé par `is_root_fork_move`.
  - `[ARCHI]` `sort_ranked_moves` (ligne 604) duplique le comparateur de tri de `rank_root_candidates_with_worst_case_search_gate` (ligne 564) — même 4-key ordering dans deux fonctions distinctes. Seule `sort_ranked_moves` est appelée dans les tests, la fonction de production utilise le gated path.
  - `[CORRECTNESS]` `is_root_fork_move` (ligne 751) a un invariant d'appel implicite : doit être appelé *après* `simulate_action_for_search` pour que `unit.position` reflète le carré cible. Si appelé pré-move, évalue silencieusement la pièce à sa position actuelle. Aucune assertion ni commentaire n'enforce cette précondition.
  - `[PERF]` `opponent_worst_case_value` échantillonné pour jusqu'à 8 candidats par appel root — chaque appel génère tous les coups légaux de l'adversaire et les évalue. Actif par défaut (non conditionnel à un env var), coût O(branching × top-N) supplémentaire hors search principal.
  - `[CORRECTNESS]` Fallback silencieux sur `filtered_indices.first().unwrap_or(0)` (lignes 294, 560) quand la liste de candidats est vide après filtrage — retourne l'index `0` dans `ordered[]` sans validation ; peut sélectionner un coup sous-optimal si la logique de filtrage vide incorrectement les candidats.

### `src/chess/eval.rs` (355 lignes)

- **Rôle** : Évaluateur statique de position (matériel + bonus positionnels + structure de pions + sécurité du roi + mobilité + pression de conversion endgame).

- **Surface publique** :
  - `evaluate(engine, player)` — évaluation complète (pub(crate))
  - `static_evaluate(engine, player)` — alias public pour outillage
  - `terminal_score(engine, player)` — score fin de partie
  - `piece_value(kind)` — valeurs centipion (Pawn=100, Knight=320, Bishop=330, Rook=500, Queen=900, King=20000)
  - `center_bonus(pos)` — bonus positionnel central
  - `material_balance(engine, player)` — delta matériel
  - `is_winning_endgame(engine, player)` — flag endgame gagnant (≤10 pièces + avantage ≥180)
  - `endgame_conversion_pressure(engine, player)` — bonus de conversion endgame
  - `total_material_value(engine)` / `total_non_pawn_material(engine)` — totaux matériels
  - `is_low_material_search_position(engine)` / `has_non_pawn_material(engine, player)` — gardes NMP

- **Logique clé** : `evaluate` itère toutes les unités une fois en accumulant matériel + `center_bonus` + bonus spécifiques par type (structure pion, bonus roque, sécurité roi). Bonus paire de fous (+40 chaque camp). Terme de mobilité (±4/coup légal) actif seulement quand `total_units <= 20` — nécessite deux appels `legal_actions` (joueur + adversaire), O(n²) en génération. ### `src/chess/transition_reply.rs` (68 lignes)

- **Rôle** : Calcule la valeur du pire cas adversaire après un coup donné — `opponent_worst_case_value` échantillonne les réponses adversaires et retourne le minimum d'évaluation statique.

- **Surface publique** : `opponent_worst_case_value`, `WorstCaseCutoff`

- **Logique clé** : Clone l'engine, simule le coup, itère jusqu'à `opponent_worst_case_max_replies()` (défaut 12) réponses adversaires dans l'ordre de `legal_actions`, évalue statiquement chaque résultat, retourne le minimum. `WorstCaseCutoff` permet l'arrêt anticipé si le pire cas descend sous `relative_floor` ou `terminal_floor`.

- **Dépendances entrantes** : `chess::eval::static_evaluate`, `engine::*`

- **Dépendants** : `chess/mod.rs`, `chess/root_decision.rs`, `chess/transition_interpretation.rs`

- **🚩 Phase 2 flags** :
  - `[CORRECTNESS]` 🔴 **Les réponses adversaires ne sont pas triées avant l'échantillonnage** — les premiers 12 coups de `legal_actions` (ordre déterministe par `action_key`) peuvent ne pas inclure les meilleures réponses adversaires (captures fortes, échecs). La « valeur du pire cas » est une approximation heuristique, pas un vrai pire cas. Une capture de dame à l'index 25 serait manquée si `max_replies == 12`.
  - `[PERF]` Appelée pour jusqu'à 8 candidats par root call (F-026) — O(8 × 12 × static_evaluate) par coup joué, en dehors du budget search principal.
  - `[TESTS]` Zéro tests unitaires dans ce fichier — la fonction est testée indirectement via `transition_interpretation.rs` et `root_decision.rs`, mais pas isolément.
