# TACTICAL CHESS — KNOWLEDGE TRANSMISSION PROTOCOL

Purpose:
Define how Tactical Chess knowledge must be preserved, organized, and transmitted across updates, tools, and AI conversations.

---

## 1. PRINCIPLE

Every important advancement must leave a durable trace.

Preferred traces:
- structured document
- system map
- schema rule
- update report
- integration note

If knowledge exists only inside a conversation and not inside the studio, it is considered weakly preserved.

---

## 2. STORAGE RULE

Knowledge destinations:

Design authority  
→ 01_MASTER_BIBLE

Operational structural docs  
→ DOCS

Data tables  
→ 02_SYSTEM_DATABASE

Logs and generated reports  
→ 10_LOGS

Snapshots  
→ BACKUPS

Tools  
→ TOOLS

Archive-only materials  
→ 09_ARCHIVE

---

## 3. UPDATE RULE

A good update must:
- improve structure
- improve clarity
- improve transmissibility
- avoid duplicate loose files

A bad update:
- sprays files into root
- duplicates docs unnecessarily
- creates disposable bundles and leaves them behind
- changes structure without documenting it

---

## 4. AI HANDOFF RULE

To brief a new AI efficiently, the project should be transmittable through:
- AI_STARTER_PACK
- key docs in DOCS
- stable studio structure

The user should not need to re-explain the entire project.

---

## 5. CLEAN ROOT RULE

TACTICAL_CHESS_STUDIO root should remain sparse.

Loose files should be minimized.

Documents belong in DOCS.
Tools belong in TOOLS.
Temporary packages should be removed or archived.

---

## 6. EXECUTABLE RULE

Executables should:
- centralize docs
- log what they did
- clean temp artifacts
- never duplicate files without reason
- preserve backups when needed

---

## 7. SUCCESS CRITERION

The project is well transmitted when:
- another AI can understand it quickly
- another developer can navigate it quickly
- updates improve order instead of reducing it
- the studio becomes easier to maintain over time
