Pourquoi : forcer Stockfish et KataGo dans une interface commune détruit leurs performances. Garder les moteurs spécialisés et n'abstraire que les traces — c'est là que la généralisation est possible sans perte.

Contraintes : chaque moteur nécessite un adaptateur distinct. L'adaptateur chess est le premier et sert de référence. L'adaptateur Othello est le test de validation. Si le LLM clusterise les erreurs Othello avec le même code que chess, l'architecture est validée.

**35. φ(T) extracteur déterministe — 4 scalaires**

Origine : Rocky V3. L'extracteur doit être 100% déterministe, zéro ML, zéro LLM dans la boucle critique.

Pourquoi : si l'extracteur utilise du ML ou du LLM, il introduit de la non-déterminisme dans le signal. La reproductibilité des benchmarks et la fiabilité du coaching dépendent de la déterminisme de cet extracteur.

Contraintes : pas de "pattern detection ML". Chaque scalaire doit être calculable depuis les logs bruts avec une formule arithmétique. Si une valeur ne peut pas être calculée de façon déterministe, elle ne fait pas partie de φ(T).

**52. Curriculum 4 étages + replay buffer + gate de régression**

**60. FiLM conditioning — f(board, φ(T)) → policy + value**

Pourquoi : avant de patcher le training, vérifier que le runtime exploite ce que le training produit. Si ce n'est pas le cas, améliorer le training ne change rien à la performance.

Contraintes : audit uniquement — pas de patch pendant l'audit. Lire le code sans hypothèses préalables. Le résultat de l'audit définit la priorité du prochain patch.

**76. Cycle de vie autonome du studio**

Origine : session 1 Rocky/Studio, comme vision centrale de l'architecture. Reformulé et précisé tout au long de cette conversation. L'idée n'est pas nouvelle — elle est présente dès le premier résumé — mais sa formulation concrète et implémentable n'a émergé qu'en croisant les trois sessions avec les conversations Gemini.

Où ça mène : un studio qui s'améliore sans supervision constante. Pas des phases linéaires figées. Un système où les agents s'activent et se désactivent selon l'état réel mesuré par φ(T). La structure émerge des données plutôt que d'être codée en dur. Concrètement : studio_end.py calcule φ(session), Qwen lit φ et l'historique, Qwen recommande le type de session suivante, studio_start.py injecte ce brief, la session suivante est conditionnée par la dynamique des sessions précédentes, et la boucle recommence indéfiniment sans intervention humaine entre les cycles.

Pourquoi : le problème fondamental du studio solo n'est pas le manque d'idées ni le manque de code. C'est le coût de coordination — reconstruire le contexte, décider quoi faire ensuite, évaluer si la dernière session a été productive. Ces trois tâches consomment 30 à 40% du temps de travail réel. Le cycle de vie autonome externalise ces trois tâches vers les agents. Tu interviens uniquement sur les HumanGates réels — les décisions irréversibles, les commits Rust, les redirections de dataset. Tout le reste tourne seul.

La différence avec un simple script d'automatisation : un script suit des règles statiques. Le cycle de vie autonome suit la dynamique réelle du studio telle que mesurée par φ(T). Si trois sessions consécutives ont une Entropy haute et zéro commit, le système détecte ce pattern et contraint la session suivante vers un scope unique et mesurable. Si une session produit un Shock élevé, la suivante commence par un audit plutôt qu'une nouvelle construction. Les règles émergent des données, pas l'inverse.

La différence avec les systèmes multi-agents classiques : la plupart des architectures multi-agents supposent des rôles fixes et des workflows prédéfinis. Le cycle de vie autonome du studio utilise φ(T) comme signal universel qui traverse tous les agents — Rocky, Claude, Qwen, Devstral. Chaque agent lit le même signal et l'interprète selon son rôle. Il n'y a pas de coordinateur central qui décide tout — il y a un signal partagé que chaque agent interprète localement.

Les six primitives du cycle, dans l'ordre :

Observation — Claude ou studio_end.py lit φ(session courante) et φ_history.

Reflection — que signifie ce φ dans le contexte de l'historique ? Quel régime ? Quelle tendance ?

Intention — Qwen CEO propose une direction pour la prochaine session basée sur l'analyse.

Action — le studio exécute. Claude Code implémente, les chaînes LangGraph tournent, les benchmarks se lancent.

Feedback — φ(session suivante) est calculé. Les métriques changent ou non.

Loop — sans fin, sans supervision constante.

Contraintes : c'est la dernière idée à implémenter, pas la première. Elle présuppose que tout le reste fonctionne — φ_history.jsonl rempli avec au moins dix sessions, studio_end.py stable, Qwen calibré sur au moins le Tier 1, les graphes LangGraph validés sur des cas réels. Mettre le cycle autonome sur une fondation instable produit un système qui dérive de façon invisible — exactement le scénario le plus dangereux pour un studio solo sans supervision externe.

La contrainte la plus importante est psychologique autant que technique : un cycle autonome ne signifie pas un cycle sans pilote. Tu restes le HumanGate sur toutes les décisions irréversibles. Le cycle autonome gère la coordination et la mémoire inter-sessions. Toi tu gères les décisions à conséquences réelles. Cette frontière doit être explicite et documentée dans le système dès le premier jour, sinon le cycle dérive vers des décisions qu'il ne devrait pas prendre.
