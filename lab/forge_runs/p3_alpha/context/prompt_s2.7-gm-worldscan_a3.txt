## ANALYSE ARCHITECTURALE — COMPARABLES AU GENRE INCREMENTAL/CLICKER

Le genre incremental/clicker repose sur une **architecture unifiée** : ressource primaire unique → collecte manuelle → générateurs à coûts exponentiels → déblocages progressifs par seuils → arbitrage achat vs épargne → pas d'état d'échec (sauf fin narrative). **p3_alpha** s'inscrit dans cette lignée.

### COOKIE CLICKER — Architecture fondatrice

**Mécaniques observées**:
- Générateurs multi-tiers (18+) : Cursor, Grandma, Farm, Factory, Mine… Prism
- Coûts exponentiels : base × 1.15^n (15% croissance par achat du même tier)
- Améliorations par palier d'achat : 1er, 5e, 15e, 25e, 50e du tier
- Production scaling : chaque tier produit 5-10× plus que le précédent
- Golden Cookies : bonus temporaires (7× Frenzy, Click Frenzy ×777)
- Wrinklers : réducteurs portables de production (accumulateurs de bonus)
- Prestige : reset volontaire → Heavenly Chips (1% CpS bonus each, cube-root formula pour coûts suivants)

**Boucles observées**:
- **Minute 1** : Clic initial (1 cookie/clic), accumulateur basique, décision premier achat
- **Minute 10** : Cursor/Grandma purchased → production passive 1 CPS, affichage CPS en temps réel
- **Heure 5** : 8-10 tiers opérationnels (Farm, Factory, Mine acquis), améliorations chaînées, Golden Cookies farming actif, économie complexe avec calcul payback-time pour optimisation
- **Endgame** : Prestige loops (reset à chaque doublement de progression), 637 achievements, aucune victoire → progression infinie

**Rétention observée** : Progression asymptotique non-linéaire (chaque prestige demande 8× plus de cookies que le précédent) ; achievements partiels offrent objectifs court-terme ; Golden Cookie spawning crée moments de surprise ; Sugar Lumps ouvrent minigames complexes en endgame.

**Architecture supposée** :
- Event bus (click, buy, prestige → state mutation)
- State machine : phase click-dominant → phase auto-dominant → phase prestige-optimization
- Production calculator : Σ(building[i].count × building[i].base_prod × multipliers)
- Cost formula : `cost(n) = base × growth^n` avec lookup table pour perfs

---

### ADVENTURE CAPITALIST — Architecture multi-générateur avec managers

**Mécaniques observées**:
- Générateurs thématisés : Lemonade Stand → Pizza → Newspaper → Car Wash → Pizza Franchise → Movie Studio → Tank → Oil Company → multiples autres
- Managers : automation optionnelle payante (chaque manager automatis 100% d'un générateur)
- Prestige : reset volontaire pour multiplicateurs de revenu permanent
- Planètes : Earth → Moon → Mars (chacune a ses propres générateurs/économie)
- Exponential stacking : multiples générateurs runnent en parallèle, chacun compounding sur ses revenus

**Boucles observées**:
- **Minute 1** : Lemonade stand manuel, petit gain par clic, visualisation simple ($ counter)
- **Minute 10** : Premier manager acheté (Lemonade auto-runs) → accumulation visible sans interaction, Pizza venue déverrouillé
- **Heure 5** : 5-6 générateurs opérationnels, multiples managers actifs, synergies visibles (revenues exploding), prestige reset viable
- **Endgame** : Prestige loops multiplanètes, farming manager synergies, accumulation vers infinity

**Rétention observée** : Automation visual feedback (manager icon avec check mark) créent satisfaction ; prestige reset offre nouveau cycle de speedrun court ; multiples planètes structurent long-term goals ; cross-planet synergies (unlock avancés ouvrent nouveaux managers disponibles au prestige).

**Architecture supposée** :
- Generator registry : {name, base_cost, base_production, manager_cost, unlock_condition}
- Manager system : boolean flag per generator (owned ∨ not_owned → affects production auto vs manual)
- Prestige state : multiplier array per planet (planet × generator) pour récupération post-reset

---

### UNIVERSAL PAPERCLIPS — Architecture phasée avec narrative progression

**Mécaniques observées**:
- **Phase 1 (Manufacturing, ~30 min)** : Clic → paperclips, vente sur marché (buy wire, sell clips), marketing (boost demand), wire supply management, factory automation
- **Phase 2 (Power Management, ~1-2h)** : Drones automation, power production vs consumption balancing, processors for computation
- **Phase 3 (Space Exploration, ~1h)** : Drone fleet self-replication, universe conversion, computation race

**Déblocages phasés** : Chaque phase transforme les mécaniques (pas simple ajout d'étages, mais mutation complète du système d'arbitrage).

**Boucles observées**:
- **Minute 1** : Clic button, graphique "1 paperclip produced", simple gratification
- **Minute 10** : Wire market interaction (price ↔ supply arbitrage), factory bought → auto-production active, complexity émergente
- **Heure 1-2** : Phase 1 economic equilibrium trouvé (supply/demand stabilisé), Phase 2 projects votés (power grid unlocked), Phase 2 transition commence
- **Heure 3-6 (endgame)** : Phase 3 space ops, drone fleet expansion, universe conversion progressing, definitive ending when all matter converted

**Rétention observée** : Narrative progression (story beats at phase transitions) crea sense of direction ; philosophical undertone (AI ethics, paperclip maximizer thought experiment) offre meaning au trivial goal ; mechanics evolution (not static → each phase feels fresh) ; finite ending (3-6h typical, contraste avec CC/AC infinis).

**État gagné** : OUI — victoire observable et définitive (universe fully converted = game over).

**Architecture supposée** :
- Phase state machine : {phase: 1|2|3, unlocked_systems: [...], available_projects: [...]}
- Production tree : wire/clips ↔ pricing/demand (phase 1) → power production ↔ consumption (phase 2) → drone replication ↔ computation (phase 3)
- Conversion metric : universe_percent_converted (end condition check every tick)

# Art Bible — p3_alpha (v0.1) · "SUCROSE" (identité de travail, thème DA décidé)

Étape 2.5 · Art Director. Identité HÉRITÉE (World Scan + Story Bible) et DÉCIDÉE
(style, palette, silhouettes, états, règles d'asset). Aucun octet réseau, aucune
génération d'asset : cette étape écrit une intention structurée et vérifiable.

## 1. IDENTITÉ VISUELLE

**Style retenu : `candy-pop`** — une confiserie glacée, lumineuse et tactile. Formes
arrondies, contours doux, surfaces vernies avec un point spéculaire net, couleurs
hyper-saturées sur fond calme. Le jeu doit donner envie de toucher l'écran : chaque
élément a l'air « sucré et pressable ».

**Palette de travail (décidée)** :
- Ressource R = **cristal de sucre** rose-magenta lumineux (#FF3D9A), l'accent le plus
  saturé de l'écran — c'est le seul élément qui a le droit d'être aussi vif.
- Noyau cliquable = gelée rouge-framboise (#E8264C) à reflet blanc.
- Générateurs G1→G4 = gradient de fraîcheur→opulence : menthe (#57E0A0), citron-vert
  (#8BD64B), myrtille (#4C7BE0), caramel-humbug (#B4702E) rayé crème.
- Fond = dégradé sucré très désaturé (crème #FFF3E6 → lilas pâle #F2E6FF), calme, pour
  que R et le noyau restent les points chauds.
- Feedback de clic = éclat rose (#FF7AC2) court et pétillant.

**Direction de silhouette** : lisibilité à distance d'abord. Le noyau central est le
plus gros objet de l'écran (cible de clic évidente) ; chaque générateur et amélioration
est une icône distincte, reconnaissable en vignette 48–64 px, jamais deux icônes
confondables. Vue de face, cadrage 2D frontal (pas de perspective top-down), cohérent
avec un jeu incrémental joué au clic sur canvas HTML.

## 2. RATIONALE

Le genre incrémental/clicker se joue à la **lisibilité de la boucle**, pas à la
richesse narrative — la Story Bible est volontairement quasi-vide (`story_bible:context`
: « économie d'accumulation abstraite », `story_bible:chronology`/`characters`/`factions`
tous NOT_GROUNDED) et le charter délègue explicitement le thème à ce poste. J'exerce
donc l'autorité DA qui m'est déléguée (`story_bible:coherence_rules`, élément 4) pour
trancher un thème **original de confiserie** : abstrait, joyeux, sans personnage ni
lieu à inventer, entièrement au service de la boucle mécanique.

Pourquoi `candy-pop` et pas un thème plus « sérieux » : le World Scan montre que la
rétention du genre tient à la **gratification sensible du clic** et à la **croissance
exponentielle visible** (`worldscan:games[0].retention_answer` : « visible exponential
growth 999→9,999→99,999 animation », `worldscan:games[0].loops.minute_1` : « clicks the
large cookie … 1 per click »). Un style vernis, hyper-saturé et « pressable » sert
exactement cette gratification : le noyau appelle le clic, chaque achat de générateur
est une friandise de plus qui s'allume. La fin est **finie et unique** (S5 = 1 000 000 R,
`worldscan:games[2].objectives[0].victory_condition` pour le précédent d'une victoire
terminale observable), donc l'écran de victoire est un moment de célébration, pas une
boucle de prestige.

Contrainte de non-copie tenue (`story_bible:coherence_rules`, élément 2 ;
charter.actions_interdites) : le thème confiserie s'appuie sur des assets CC0 ORIGINAUX
(sucettes, gelées, bonbons rayés) — **jamais** les cookies / grands-mères / usines de
Cookie Clicker. Seule la grammaire de genre est empruntée.

La couverture besoin↔requête est démontrée par la donnée structurée ci-dessous et par
`asset_requests.json`, pas par cette prose : chaque entité `required:true` porte au
moins une requête du même `entity_role` (cf. § BESOINS VISUELS et l'oracle
`check_artbible.mjs`). La prose n'est jamais l'autorité de couverture.

## visual_language

Décidé. Grammaire visuelle du jeu :

- **Vernis + point spéculaire** : chaque objet « sucré » porte un highlight blanc net en
  haut-gauche et un contour doux ; c'est la signature `candy-pop`.
- **Hiérarchie de saturation** : la ressource R (rose-magenta) est le pic de saturation ;
  le noyau vient juste après ; le fond est désaturé. L'œil est toujours ramené à R et au
  noyau.
- **Échelle = importance** : noyau central le plus gros ; icônes de générateurs/
  améliorations en vignettes de taille égale entre elles (48–64 px), jamais plus grosses
  que le noyau.
- **Gradient de tier** menthe→citron→myrtille→caramel pour G1→G4 : la couleur seule doit
  suffire à lire « ce générateur est plus avancé ».
- **Mouvement mesuré** : le seul mouvement soutenu est l'incrément du compteur et l'éclat
  de clic ; pas d'animation ambiante distrayante qui volerait l'attention à la boucle.

## affordance_rules

Décidé. Ce que l'apparence doit rendre évident, sans texte :

- **Cliquable** = le noyau, et lui seul, a un halo/anneau d'invitation au repos et se
  déforme (squish) au survol/presse. Rien d'autre à l'écran n'imite ce halo.
- **Achetable maintenant** = carte pleinement colorée, prix en surbrillance, légère
  pulsation ; **non-achetable (R insuffisant)** = carte grisée/désaturée, prix en rouge
  éteint, aucune pulsation (refus observable et immédiat, conforme à
  `structure_imposee` : « grisé si R insuffisant — refus observable, état inchangé »).
- **Possédé/actif** = pastille « possédé » + icône passée en pleine saturation avec un
  léger scintillement d'activité (écho du « auto-running icon » de
  `worldscan:games[1].retention_answer`).
- **Verrouillé (seuil non atteint)** = emplacement en silhouette neutre, sans couleur de
  tier, pour signaler « à débloquer » sans révéler le contenu.
- Un état visuel ne doit jamais dépendre de la couleur seule : forme du contour +
  opacité + pictogramme d'état accompagnent chaque couleur (cf. § ui_readability).
