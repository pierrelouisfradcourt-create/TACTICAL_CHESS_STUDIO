## Décision d'architecture (résumé)

Découpage par **responsabilité**, en couches strictement orientées pour garder le noyau logique pur (DOM-free, exécutable sous `node --test`) — c'est la contrainte structurante du charter (`plateforme_cible_detail` : « aucun module logique ne touche `document/window/canvas/Date/performance/Math.random` »).

```
index.html ──▶ main.mjs ──▶ { render, input } ──▶ { sim, actions } ──▶ config
   (DOM shell)  (compo root)   (DOM adapters)        (noyau pur)      (données figées)
                                    bots ──▶ { sim, actions, config }   (drivers headless)
                                    tests ──▶ { sim, actions, bots, config }
```

- **`config`** (feuille, 0 dép) : tables figées — géométrie 20×12 + chemin en épingle, stats tours/ennemis, calendrier 10 vagues, tables de coût d'upgrade, `TICK_MS`. Contenu, jamais comportement.
- **`sim`** : noyau de simulation déterministe pur (rng seedé porté dans l'état, `step(state,dt)`, mouvement/chemin, ciblage `first`, combat/armure, économie, vagues, upgrades, fin de partie, hash d'état). Dépend seulement de `config`.
- **`actions`** : API d'écriture UNIQUE — valide puis applique chaque intent joueur (place/upgrade/select/call-wave/restart) et refuse en UN point les actions invalides (R41). Consommée par `input` ET `bots`.
- **`render`** : dessin canvas 2D, **lecture seule** de l'état.
- **`input`** : DOM → intents (via `actions` uniquement, jamais `sim` directement).
- **`bots`** : politiques scriptées headless (compétent/naïf/tall/wide/mixte/tempo) qui pilotent `actions` — instrument des preuves de solvabilité et de variance.
- **`main.mjs`** : racine de composition — boucle rAF qui accumule le temps réel et n'avance `sim.step` que par pas fixe (frontière temps-réel→pas-fixe, R31), expose `window.__game` en lecture seule.
- **`index.html`** : page unique, ancrages DOM (canvas 640×384, boutons, `#overlay`, `#restart`), zéro dépendance externe.

**God-objects tués avant naissance** : le contenu (`config`) est séparé du moteur ; l'écriture d'état passe par un seul point (`actions`), donc ni `input` ni `bots` ne pokent le noyau ; `render` est read-only.
