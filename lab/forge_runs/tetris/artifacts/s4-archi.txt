## 2 — Graphe de dépendances

### Autorisées (DAG, une seule direction)
```
07_TESTS ─────────────▶ 05_SYSTEMS   (tests exercent la logique pure)
07_TESTS ─────────────▶ 06_RUNTIME   (tests exercent les adapters)   [exempts d'oracle: _is_test_file]
06_RUNTIME ───────────▶ 05_SYSTEMS   (les adapters PILOTENT la logique : rendu lit l'état, input pousse des intents)
solvability (racine) ─▶ 05_SYSTEMS   (le bot exerce la LOGIQUE headless)
runtime_loop ─────────▶ game_loop    (la boucle runtime tick la logique)
input_adapter ────────▶ input_rules  (clavier → intent → validation pure)
presentation ─────────▶ game_state / piece_bag / scoring  (rendu = lecture seule de l'état)
```
`05_SYSTEMS` n'a **aucune** dépendance sortante hors de lui-même : la logique est le cœur pur. Le graphe est **acyclique** (aucune arête retour).

### Interdites (déclarées explicitement — le cœur du garde-fou)

| # | Arête interdite | Justification architecturale |
|---|---|---|
| 1 | `05_SYSTEMS → 06_RUNTIME` | **La logique ne connaît jamais la couche runtime.** Superset qui attrape rendu + input + persistance. Sans lui, R1–R9 ne seraient plus testables headless. |
| 2 | `05_SYSTEMS → presentation` | **logique → rendu INTERDIT** (mandat explicite). La logique ne dessine rien ; le rendu lit l'état, jamais l'inverse. Tue le god-object « système qui s'affiche ». |
| 3 | `05_SYSTEMS → input_adapter` | **logique → input INTERDIT** (mandat explicite). La logique lit des **intents** (`input_rules`), jamais le clavier physique. C'est ce qui rend R6 prouvable sans périphérique. |
| 4 | `05_SYSTEMS → 07_TESTS` | Le code de production ne dépend jamais du code de test (sinon inversion de la preuve). |
| 5 | `06_RUNTIME → 07_TESTS` | Un adapter runtime ne dépend jamais des tests. |
| 6 | `solvability → presentation` | Le bot de solvabilité prouve la **jouabilité de la logique** en headless — il ne doit pas dépendre du rendu (sinon la preuve de solvabilité devient une preuve d'affichage). |
| 7 | `solvability → input_adapter` | Le bot **génère ses propres coups** ; dépendre de l'input humain invaliderait la preuve « un bot joue seul ». |

> **Note d'honnêteté sur la granularité de l'oracle** : `check_architecture` voit un fichier-source par son **premier segment** sous `games/tetris` (`_module_of`). Les arêtes #2/#3/#6/#7 utilisent des noms de **sous-dossier/fichier** (`presentation`, `input_adapter`, `solvability`) qui ne matchent que côté **cible d'import** (segments de chemin `preload/load`). Elles sont donc mécaniquement vérifiables sur la cible, avec la source au grain top-level. Les deux endpoints de chaque paire figurent dans `modules` (condition nécessaire pour que l'intersection `imported & modules` laisse l'arête se déclencher).

> **Limite assumée (non masquée)** : les dépendances **intra-`05_SYSTEMS`** (ex. « `piece_bag` ne doit pas importer `line_clear` ») ne sont **pas** exprimables comme arêtes interdites avec cet oracle (tout fichier de 05_SYSTEMS a `src_mod == 05_SYSTEMS`, donc une paire `["05_SYSTEMS","line_clear"]` frapperait aussi les imports légitimes). Elles sont déclarées comme **invariants d'architecture** ci-dessous, pas comme oracle — c'est un fait de conception, remonté honnêtement, pas un oubli. → **fog G-A** (voir §6).
