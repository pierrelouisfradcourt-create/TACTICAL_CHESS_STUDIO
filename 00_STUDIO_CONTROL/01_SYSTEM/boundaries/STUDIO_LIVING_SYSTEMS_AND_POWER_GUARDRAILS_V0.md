## Purpose

This document records Studio-wide boundary rules for living systems, human
feedback, creative tooling, and resource power.

The Studio builds AI-assisted tools for video game creation, creative
production, documentation, QA, and bounded development workflows.

The Studio does not build world-governance AI, surveillance AI, coercive AI,
military AI, or autonomous systems acting on real-world infrastructure.

This document is a canonical boundary document. It does not authorize
implementation, runtime activation, agent activation, training, dataset
generation, benchmark claims, model promotion, legal compliance claims, Git
actions, or infrastructure control.

## Scope

This boundary applies to Studio Control, GPT Navigator prompts, Codex task
framing, local review, future operator profiles, future agent designs, future
dataset discussions, future model discussions, and future automation loop
discussions.

It governs posture and routing. It is not runtime code, a product requirement,
a legal opinion, a compliance certification, a research approval, or a mandate
to build any external governance system.

## Origin Rationale

These guardrails arrived after human concern that the Studio was touching
advanced topics with real social, ethical, operational, and resource
implications.

The concern was valid as a boundary signal. It does not mean the Studio is
building real-world governance AI. It means the Studio must name the boundary
before building stronger local pipelines, agents, tools, datasets, checkpoints,
or automation loops.

The actual Studio mission remains video game creation and creative tooling. The
living-systems doctrine is an ethical and operational boundary, not runtime
authority.

## Living Systems Doctrine

The Studio treats humans, players, creators, communities, cultures, ecosystems,
and living feedback loops as dignity-bearing systems, not extractive resources.

The Studio must preserve:

- real feedback
- human authorship
- HumanGate
- player dignity
- ecological awareness
- creative diversity
- cultural plurality
- play as exploration
- bounded expansion
- auditability
- reversibility

Real human/player feedback must be treated as dignity-bearing feedback, not as
data livestock.

Synthetic loops may assist exploration, but must not replace real feedback
indefinitely.

Growth is not intelligence. Control is not understanding.

## Gardeners, Not Zookeepers / Matrix Farmers / Terminator Builders

We are gardeners, not zookeepers, not Matrix farmers, not Terminator builders.

This posture means the Studio may cultivate creative tools, safer workflows,
better documentation, better QA, better design iteration, and healthier
feedback loops.

It must not turn humans, players, agents, or creative communities into managed
inventory, captive data sources, coercive targets, or passive fuel for
automation.

The Studio should prefer cultivation over control, consent over extraction,
bounded experiments over open-ended expansion, and reversible workflows over
irreversible automation.

## Studio Mission Boundary

The Studio mission is AI-assisted video game creation and creative tooling.

Allowed mission areas include:

- game design support
- content and documentation tooling
- bounded development workflows
- QA support
- prompt and report hygiene
- passive red-team review
- patch-chain planning
- creative production support
- local review and audit tooling

The Studio mission excludes:

- world governance
- surveillance
- coercion
- military targeting
- autonomous infrastructure action
- real-world enforcement systems
- hidden agent expansion
- uncontrolled resource scaling

## World Protector Classification

World Protector remains philosophical, fictional, and roadmap-excluded unless a
later HumanGate creates a separate legal and governance research track.

World Protector must not be converted into operational requirements, product
requirements, agent requirements, dataset requirements, training goals, runtime
goals, benchmark targets, or deployment plans inside the Studio.

If World Protector language appears in future notes, it must be classified as
fictional, philosophical, or roadmap-excluded by default.

## Player and Human Dignity

Players are not data livestock, compliance objects, or automated retention
targets.

Human authorship must remain visible where creative or governance decisions are
made. HumanGate must remain the final decision point for promotion, activation,
training, benchmark claims, model promotion, dataset use, and irreversible
workflow changes.

Creative diversity and cultural plurality are Studio assets. The Studio should
not collapse diverse play styles, feedback styles, cultural references, or
creative signals into a single optimization target.

## Real Feedback Requirement

Real feedback is required for claims about player experience, creative quality,
usability, or human value.

Synthetic review, model critique, local inference, generated reports, and
automated loops may support exploration, but they do not prove human value.

Any claim based only on synthetic feedback, local model review, or internal
automation must remain bounded, labeled, and non-final.

## Bounded Expansion

The Studio may expand tools and workflows only through bounded steps.

Each expansion must declare:

- purpose
- owner surface
- output route
- blocked actions
- expected validation
- stop condition
- HumanGate decision when authority changes

Unbounded expansion is blocked. Open-ended loops are blocked. Autonomous
scaling is blocked. Background agent growth is blocked.

## Studio Power Governance

Compute, energy, storage, time, attention, agents, datasets, checkpoints, and
automation loops are bounded resources.

No heavy process may run without explicit purpose, estimated cost, resource
limit, time limit, stop condition, expected output, output routing, and
HumanGate when applicable.

Default posture:

- smallest useful run
- no uncontrolled expansion
- no open-ended loops
- no autonomous scaling
- no compute without evidence purpose

Power governance applies to local models, Codex tasks, data processing,
automation loops, indexing, future RAG, future LoRA work, future evaluations,
future agents, and future build or runtime tasks.

## Heavy Process Gate

A heavy process is any task that may consume meaningful compute, energy,
storage, operator attention, model context, dataset space, checkpoint space, or
automation time.

Before a heavy process runs, the task must declare:

- purpose
- expected value
- estimated cost
- resource limit
- time limit
- stop condition
- expected output
- output routing
- owner surface
- blocked actions
- HumanGate requirement

If any required field is UNKNOWN, the process is BLOCKED.

HumanGate is required before:

- any authority promotion
- any source promotion
- any runtime activation
- any model promotion

- any benchmark proof claim
- any agent activation

review, demand legal review, or demand source readback.
